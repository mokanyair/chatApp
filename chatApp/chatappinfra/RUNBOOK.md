# ChatApp Infrastructure Runbook

## Prerequisites

| Tool | Minimum version |
|---|---|
| Terraform | >= 1.6 |
| AWS CLI | authenticated with sufficient IAM permissions |
| kubectl | any recent version |
| helm | >= 3.x |

Before every session, confirm your IP is current in `terraform.tfvars`:

```bash
curl -s https://checkip.amazonaws.com
# Update cluster_endpoint_public_access_cidrs = ["<your-ip>/32"] if it changed
```

---

## Deployment — Phase by Phase

### Phase 0 — Bootstrap (first time only)

Creates the S3 state bucket, DynamoDB lock table, and runs `terraform init`.
Safe to re-run — all operations are idempotent.

```bash
cd chatappinfra
bash scripts/bootstrap.sh
```

If the bucket or table already exists the script skips creation and goes
straight to `terraform init`.

### Phase 0b — Init (every session after cloning or resetting)

```bash
terraform init
```

---

### Phase 1 — Foundation

Creates KMS keys, VPC, subnets, NAT gateways, security groups, and the
IAM roles that EKS needs before the cluster exists.

```bash
terraform apply \
  -target=module.iam_bootstrap \
  -target=module.vpc \
  -target=module.kms \
  -target=module.security_groups \
  -auto-approve
```

Expected time: ~3 min. Expected resources: ~45.

---

### Phase 2 — EKS Cluster

```bash
terraform apply -target=module.eks -auto-approve
```

Expected time: ~15–20 min. Expected resources: ~8.

Why separate: the `helm` and `kubernetes` Terraform providers authenticate
against the EKS API endpoint. That endpoint doesn't exist until the cluster
is created, so a cold full apply fails. Creating EKS first lets Terraform
resolve the provider configs before the next phase.

---

### Phase 3a — External Secrets Operator (bootstrap for CRDs)

The `ClusterSecretStore` resource (kind from ESO) is validated at plan time.
If ESO is not installed yet, the plan fails with
`no matches for kind "ClusterSecretStore"`. Install ESO first to register
its CRDs, then do the full apply.

```bash
terraform apply \
  -target=module.iam \
  -target=kubernetes_namespace.external_secrets \
  -target=kubernetes_service_account.external_secrets \
  -target=helm_release.external_secrets \
  -auto-approve
```

Expected time: ~2 min. Expected resources: ~15.

---

### Phase 3b — Full Apply

```bash
terraform apply -auto-approve
```

Creates: Aurora MySQL writer + reader, ElastiCache Redis, ACM certificate +
Route53 DNS validation, WAF WebACL + S3 access-log bucket, Secrets Manager
secrets, remaining IAM IRSA roles, K8s namespaces / service accounts /
NetworkPolicy / PDB / ResourceQuota, Helm operators
(ALB controller, metrics-server, cluster-autoscaler), and generates both
Helm values files.

**Important — SG rules for RDS and Redis are applied here, not in Phase 1.**
`aws_security_group_rule.eks_cluster_to_rds` and
`aws_security_group_rule.eks_cluster_to_redis` depend on
`module.eks.cluster_sg_id` (the auto-created EKS cluster SG that is actually
attached to nodes), so they can only be created after Phase 2. If Phase 3b
fails partway through and you re-run it without these rules landing, pods will
get `ETIMEDOUT` (error 110) connecting to RDS/Redis. Verify with:

```bash
aws ec2 describe-security-groups --region us-east-1 \
  --filters "Name=group-name,Values=chatapp-prod-rds-sg" \
  --query 'SecurityGroups[*].IpPermissions'
# Should show TWO ingress rules: one for eks_nodes_sg, one for eks-cluster-sg
```

Expected time: ~15–20 min (RDS and ElastiCache dominate).

**If this fails with secrets in recovery window:**

```bash
aws secretsmanager delete-secret \
  --secret-id chatapp/prod/db-credentials \
  --force-delete-without-recovery --region us-east-1
aws secretsmanager delete-secret \
  --secret-id chatapp/prod/redis-auth-token \
  --force-delete-without-recovery --region us-east-1
aws secretsmanager delete-secret \
  --secret-id chatapp/prod/app-config \
  --force-delete-without-recovery --region us-east-1
# Then re-run terraform apply -auto-approve
```

---

### Phase 4 — RDS CA Certificate

Required once. The cert is uploaded into a K8s Secret so the app can verify
the Aurora TLS connection.

```bash
curl -sL https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem \
  -o global-bundle.pem
```

Place the file in `chatappinfra/`. Re-run `terraform apply` if you download
it after the initial apply so it gets picked up by `kubernetes_secret.rds_ca_cert`.

---

### Phase 5 — Deploy the Application

After `terraform apply`, both Helm values files are auto-generated:

| File | Generated by | Contains |
|---|---|---|
| `awschatapp-platform/values-prod-infra.yaml` | `local_file.helm_values_infra` | DB/Redis endpoints, subnets, cert ARN, WAF ARN, image tag |
| `awschatapp-platform/values-prod-secrets.yaml` | `local_file.helm_values_secrets` | DB password, Redis auth token, app secret key |

```bash
# Update kubeconfig
aws eks update-kubeconfig --name chatapp-prod-cluster --region us-east-1

# Deploy
cd /path/to/chatApp
helm upgrade --install chatapp ./awschatapp-platform \
  --values ./awschatapp-platform/values.yaml \
  --values ./awschatapp-platform/values-prod-infra.yaml \
  --values ./awschatapp-platform/values-prod-secrets.yaml \
  -n chatapp --create-namespace
```

After Helm deploys, if pods don't restart automatically to pick up a new
secret (the pod template hash won't change when only secret content changes):

```bash
kubectl rollout restart deployment chatapp-api -n chatapp
kubectl rollout status deployment chatapp-api -n chatapp --timeout=180s
```

## Repeating from Scratch (new environment or account)

1. Edit `terraform.tfvars` — new `environment`, `cluster_name`, your IP CIDR.
2. Edit `scripts/bootstrap.sh` — new `BUCKET` and `TABLE` names.
3. Run `bash scripts/bootstrap.sh`.
4. Follow Phases 1–5 above.

## Teardown

Teardown has several mandatory pre-steps and known failure modes.
Follow the sequence below exactly to avoid getting stuck.

---

### Step 1 — Uninstall the app Helm chart

```bash
helm uninstall chatapp -n chatapp
```

Wait for the uninstall to finish before continuing. The ALB Load Balancer
Controller will begin deleting the ALB; give it ~60 s to finish.

---

### Step 2 — Pre-flight: patch Terraform sources before destroying

Two resources block a clean destroy if left at their defaults:

**a) RDS deletion protection** — Aurora has `deletion_protection = true`
by default in this repo. Terraform destroy will fail with
`InvalidParameterCombination: Cannot delete a cluster with deletion protection enabled`.

In `modules/rds/main.tf`:
```hcl
deletion_protection = false
skip_final_snapshot = true
```

**b) WAF ALB-logs S3 bucket** — If the bucket is not empty Terraform fails
with `BucketNotEmpty`. The bucket is already set to `force_destroy = true` in
`modules/waf/main.tf`; verify this is present before proceeding.

After editing, apply the changes (just those two modules):
```bash
terraform apply -target=module.rds -target=module.waf -auto-approve
```

---

### Step 3 — Manually delete the ALB

The ALB is created by the Kubernetes Load Balancer Controller, not by
Terraform, so Terraform cannot delete it. If it still exists when Terraform
tries to destroy the VPC/subnets/ACM cert, the destroy fails with:

```
ResourceInUseException: Certificate is in use
DependencyViolation: subnet has dependencies
```

Check whether an ALB exists:
```bash
aws elbv2 describe-load-balancers --region us-east-1 \
  --query 'LoadBalancers[?contains(LoadBalancerName, `chatapp`)].{Name:LoadBalancerName,ARN:LoadBalancerArn,Protection:LoadBalancerArn}' \
  --output table
```

If one exists, disable deletion protection and delete it:
```bash
ALB_ARN=$(aws elbv2 describe-load-balancers --region us-east-1 \
  --query 'LoadBalancers[?contains(LoadBalancerName, `chatapp`)].LoadBalancerArn' \
  --output text)

# Disable deletion protection
aws elbv2 modify-load-balancer-attributes \
  --region us-east-1 \
  --load-balancer-arn "$ALB_ARN" \
  --attributes Key=deletion_protection.enabled,Value=false

# Delete
aws elbv2 delete-load-balancer --region us-east-1 --load-balancer-arn "$ALB_ARN"

# Wait for full deletion before proceeding
aws elbv2 wait load-balancers-deleted --region us-east-1 --load-balancer-arns "$ALB_ARN"
```

---

### Step 4 — Remove ESO CRD-backed resources from Terraform state AND comment out config

ESO installs Custom Resource Definitions for `ClusterSecretStore` and
`ExternalSecret`. When ESO is already destroyed (or during a partial destroy),
Terraform cannot validate these resources at plan time and fails with:

```
no matches for kind "ClusterSecretStore" in group "external-secrets.io"
```

**Both steps are required.** `terraform state rm` stops Terraform tracking the
resource, but the block still exists in `k8s.tf`. During `terraform destroy`,
Terraform validates every block in the config against the live Kubernetes API —
even blocks not in state — so the plan still fails unless the blocks are also
commented out.

**Step 4a — Remove from state:**
```bash
# Check if they are still in state first
terraform state list | grep kubernetes_manifest

# Remove whichever are present
terraform state rm kubernetes_manifest.cluster_secret_store
terraform state rm kubernetes_manifest.external_secret_chatapp
```

**Step 4b — Comment out the blocks in `k8s.tf`:**

Comment out both `resource "kubernetes_manifest"` blocks (lines ~82–134):
- `resource "kubernetes_manifest" "cluster_secret_store" { ... }`
- `resource "kubernetes_manifest" "external_secret_chatapp" { ... }`

**After `terraform destroy` completes — uncomment both blocks** to restore
`k8s.tf` to its production state before the next redeploy. If left commented
out, Phase 3b will not create the `ClusterSecretStore` or `ExternalSecret`,
and the app pods will start without `DB_PASSWORD` and `SECRET_KEY` and crash.

---

### Step 5 — Fix stuck terminating namespace (finalizer deadlock)

If the `chatapp` namespace gets stuck in `Terminating` state, the cause is
almost always Ingress or TargetGroupBinding resources that have
`elbv2.k8s.aws/resources` finalizers referencing a deleted ALB. Kubernetes
never removes the finalizer because the controller is gone.

**Step 5a — Detect it:**
```bash
# Check namespace status
kubectl get namespace chatapp
# Shows: Terminating — if Active, skip this step entirely

# List resources still holding finalizers
kubectl get ingress,targetgroupbinding -n chatapp
# If resources are listed, they are the blockers
```

**Step 5b — Force-remove the finalizers:**
```bash
# Patch the Ingress
kubectl patch ingress chatapp-ingress -n chatapp \
  -p '{"metadata":{"finalizers":[]}}' --type=merge

# List TargetGroupBindings — names vary per deploy
kubectl get targetgroupbinding -n chatapp -o name

# Patch each TargetGroupBinding (replace name with actual value from above)
kubectl patch targetgroupbinding k8s-chatapp-chatappa-7c6d28d1b0 -n chatapp \
  -p '{"metadata":{"finalizers":[]}}' --type=merge
```

**Step 5c — Verify and remove from state:**
```bash
# Namespace should be gone within seconds of patching
kubectl get namespace chatapp
# Expected: Error from server (NotFound): namespaces "chatapp" not found

# Remove from Terraform state so destroy doesn't try to re-delete it
terraform state rm kubernetes_namespace.chatapp
```

---

### Step 6 — Destroy Helm releases and K8s resources

```bash
terraform destroy \
  -target=helm_release.aws_lb_controller \
  -target=helm_release.external_secrets \
  -target=helm_release.metrics_server \
  -target=helm_release.cluster_autoscaler \
  -auto-approve
```

---

### Step 7 — Full destroy

```bash
terraform destroy -auto-approve
```

Expected time: ~20–30 min (RDS and ElastiCache clusters dominate).

---

### Step 8 — Fallback: targeted destroy when full destroy fails

If the Kubernetes or Helm providers fail to initialize (EKS cluster already
gone, or CRD validation errors), a naked `terraform destroy` will error at
plan time. Use a targeted approach instead:

```bash
# List everything still in state
terraform state list

# Destroy remaining non-K8s resources individually
# (EKS, IAM, KMS, security groups, VPC are safe to target directly)
terraform destroy \
  -target=module.eks \
  -target=module.iam_bootstrap \
  -target=module.kms \
  -target=module.security_groups \
  -target=module.vpc \
  -auto-approve
```

Run `terraform state list` again after each batch; repeat until the list
is empty or contains only `data.*` sources (those are read-only and harmless).

---

### VPC stuck with DependencyViolation

**Symptom:**
```
Error: deleting EC2 VPC (vpc-xxx): DependencyViolation:
The vpc 'vpc-xxx' has dependencies and cannot be deleted.
```

**Cause:** The AWS Load Balancer Controller creates security groups for each
Ingress (named `k8s-<namespace>-*` and `k8s-traffic-*`) that are not managed
by Terraform. They remain in the VPC after `helm uninstall` and block deletion.

**Fix:**
```bash
# Find LBC-owned security groups still in the VPC
aws ec2 describe-security-groups --region us-east-1 \
  --filters "Name=vpc-id,Values=<vpc-id>" \
  --query 'SecurityGroups[?GroupName!=`default`].{ID:GroupId,Name:GroupName}' \
  --output table

# Delete each one
aws ec2 delete-security-group --region us-east-1 --group-id <sg-id>

# Then retry
terraform destroy -target=module.vpc -auto-approve
```

After deleting the orphaned SGs, VPC deletion completes in ~1 s.

## Known Issues and Fixes

### LBC webhook — no endpoints available

**Symptom:**
```
Internal error occurred: failed calling webhook "mservice.elbv2.k8s.aws":
Post "https://aws-load-balancer-webhook-service.kube-system.svc:443/...":
no endpoints available for service "aws-load-balancer-webhook-service"
```

**Cause:** Terraform applied a Kubernetes `Service` or `Ingress` resource
before the AWS Load Balancer Controller pod was fully running and its
admission webhook was registered. Every Service creation is routed through
the LBC `MutatingWebhookConfiguration`; if the pod isn't answering yet,
the API server has nowhere to send the request.

**Fix:** Wait for the LBC pod to become ready, then re-run the apply.
No cleanup is needed — the resources themselves are fine.

```bash
kubectl rollout status deployment aws-load-balancer-controller \
  -n kube-system --timeout=120s

terraform apply -auto-approve
```

---

### Pods get ETIMEDOUT to RDS/Redis — EKS cluster SG not in rules

**Symptom:**
```
ERROR 2003 (HY000): Can't connect to MySQL server on '...rds.amazonaws.com:3306' (110)
```
Error code 110 = `ETIMEDOUT` — a security group is silently dropping packets
(vs. 111 = `ECONNREFUSED` which means the port is closed).

**Cause:** EKS automatically creates a cluster security group
(`eks-cluster-sg-<cluster-name>-*`) and attaches it to all node EC2 instances.
The Terraform-managed `chatapp-prod-eks-nodes-sg` is added to the cluster
*control plane ENIs* (via `vpc_config.security_group_ids`), not to nodes.
`main.tf` has the correct rules (`aws_security_group_rule.eks_cluster_to_rds`
and `aws_security_group_rule.eks_cluster_to_redis`) but they depend on
`module.eks.cluster_sg_id` and are only applied in Phase 3b. If Phase 3b
fails partway through, these rules may be missing.

**Fix:** Re-run Phase 3b, or add the rules manually:

```bash
CLUSTER_SG=$(aws eks describe-cluster --name chatapp-prod-cluster \
  --region us-east-1 \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)

RDS_SG=$(aws ec2 describe-security-groups --region us-east-1 \
  --filters "Name=group-name,Values=chatapp-prod-rds-sg" \
  --query 'SecurityGroups[0].GroupId' --output text)

REDIS_SG=$(aws ec2 describe-security-groups --region us-east-1 \
  --filters "Name=group-name,Values=chatapp-prod-redis-sg" \
  --query 'SecurityGroups[0].GroupId' --output text)

aws ec2 authorize-security-group-ingress --region us-east-1 \
  --group-id "$RDS_SG" --protocol tcp --port 3306 --source-group "$CLUSTER_SG"

aws ec2 authorize-security-group-ingress --region us-east-1 \
  --group-id "$REDIS_SG" --protocol tcp --port 6379 --source-group "$CLUSTER_SG"
```

### db-init / Alembic crash — invalid interpolation syntax in DATABASE_URL

**Symptom:**
```
ValueError: invalid interpolation syntax in
'mysql+pymysql://admin:Q-PTdCyR%$41V+CO3U!...@host:3306/db' at position 30
```

**Cause:** `random_password` was generating passwords with special characters
(`%`, `$`, `!`, `#`). When embedded raw into a connection URL, these break
multiple parsers: `%` triggers Python ConfigParser interpolation (`%(var)s`
syntax), `#` is treated as a URL fragment separator, and `$`/`!` expand in
shell contexts.

**Fix (already applied in `main.tf`):** Set `special = false` on both
`random_password` resources so only alphanumeric characters are generated.
No downstream escaping is needed.

```hcl
resource "random_password" "db" {
  length  = 32
  special = false
}
resource "random_password" "redis_auth_token" {
  length  = 32
  special = false
}
```

If you hit this on an existing deployment, force-delete the secrets (see
Phase 3b), then re-run `terraform apply` to generate new clean passwords.

### db-init job — Can't connect to MySQL (ETIMEDOUT)

**Symptom:**
```
ERROR 2003 (HY000): Can't connect to MySQL server on
'chatapp-prod-db.cluster-xxx.us-east-1.rds.amazonaws.com:3306' (110)
```

**Cause:** Error code 110 is `ETIMEDOUT` — the connection silently hung
rather than being actively refused. This is the fingerprint of a security
group dropping packets. The ingress rules allowing EKS nodes to reach RDS
on port 3306 (and Redis on 6379) had not been applied yet.

**Fix:** Apply the missing security group rules, then re-run the failed job.

```bash
terraform apply -auto-approve   # pushes the missing SG rules

# Delete the failed job pod so K8s retries it
kubectl delete pod -n chatapp -l job-name=chatapp-db-init
```

**Diagnostic tip:**
- Timeout (110) → security group silently dropping packets
- Connection refused (111) → port closed or service not listening
- Auth error after connecting → network is fine, credentials are wrong

### ESO CRD timing error at plan time

**Symptom:**
```
Error: API did not recognize GroupVersionKind from manifest
no matches for kind "ClusterSecretStore" in group "external-secrets.io"
```

**Cause:** `kubernetes_manifest.cluster_secret_store` is validated against

doesn't exist.

**Fix:** Run Phase 3a (install ESO first), then re-run the full apply.

### Secrets Manager — secret already scheduled for deletion

**Symptom:**
```
InvalidRequestException: You can't create this secret because a secret with
this name is already scheduled for deletion.
```

**Cause:** A previous `terraform apply` or `terraform destroy` left the
secrets in the 7-day recovery window. Terraform tries to create them again
and hits the name collision.

**Fix:** Force-delete all three secrets (see Phase 3b above), then re-apply.

### ESO KMS access denied

**Symptom (kubectl events):**
```
AccessDeniedException: Access to KMS is not allowed
```

**Cause:** The ESO IRSA role had `secretsmanager:GetSecretValue` but not
`kms:Decrypt`. Secrets Manager uses the customer-managed KMS key to decrypt
on behalf of the caller, so the caller needs KMS permission too.

**Fix:** Added `kms:Decrypt` and `kms:DescribeKey` on the secrets KMS key to
the ESO IAM policy in `modules/iam/main.tf`. Already applied — no action
needed on a fresh deploy.

---

### `chatapp-secret` conflict between ESO and Helm

**Symptom:** Pods start but `DATABASE_URL` and `REDIS_URL` are missing;
app falls back to hostname `db` and fails to connect.

**Cause:** Both the Helm `secret.yaml` template and the ESO `ExternalSecret`
targeted the same secret name `chatapp-secret`. ESO (with `creationPolicy:
Owner`) overwrote the Helm secret with only `DB_PASSWORD` and `SECRET_KEY`,
wiping `DATABASE_URL` and `REDIS_URL`.

**Fix:** ESO target renamed to `chatapp-aws-credentials` in `k8s.tf`.
Helm continues to own `chatapp-secret` with all four keys. Already applied.

---

### DB password / Redis auth token stale in values file

**Symptom:** `db-init` job fails with MySQL auth error; app fails with Redis
`AuthenticationError`.

**Cause:** `values-prod-secrets.yaml` was hand-maintained with passwords from
a previous Terraform run. Terraform generates new random passwords on each
fresh apply.

**Fix:** `terraform apply` now auto-generates `values-prod-secrets.yaml` via
`local_file.helm_values_secrets` in `main.tf`. Both Helm values files are
always in sync with the current Terraform state after every apply.

---

### Redis auth token breaks URL parsing (`#` in token)

**Symptom:** Redis `AuthenticationError` even after updating the token —
password appears truncated.

**Cause:** The Redis auth token contained `#`, which is the URL fragment
separator. When embedded in `rediss://:TOKEN@host:port`, everything after
`#` is silently dropped by URL parsers, sending a truncated password to Redis.

**Fix:**
- `awschatapp-platform/templates/secret.yaml` now applies `urlquery` to the
  auth token before embedding it in the URL, so special characters are
  percent-encoded automatically.
- `values-prod-secrets.yaml` stores the raw token; the template handles
  encoding.

---

### Pods don't restart after `helm upgrade` updates a secret

**Symptom:** `helm upgrade` succeeds but pods keep using old credentials.

**Cause:** Kubernetes only creates new pods when the pod template spec
changes. Secret content changes don't affect the template hash, so the
ReplicaSet isn't replaced.

**Fix:** After any credential rotation, force a rolling restart:

```bash
kubectl rollout restart deployment chatapp-api -n chatapp
kubectl rollout status deployment chatapp-api -n chatapp --timeout=180s
```

---

### Destroy: VPC DependencyViolation — orphaned LBC security groups

**Symptom:** VPC destroy hangs indefinitely with `Still destroying` ticks
for 15+ minutes, then fails with:
```
Error: deleting EC2 VPC: DependencyViolation:
The vpc 'vpc-xxx' has dependencies and cannot be deleted.
```
Or the VPC destroy times out (context deadline exceeded) while still ticking.

**Cause:** The AWS Load Balancer Controller creates two security groups per
Ingress (`k8s-<ns>-*` and `k8s-traffic-*`) directly via the EC2 API, outside
Terraform. These persist in the VPC even after `helm uninstall`.

**Fix:** Find and delete them while the VPC destroy is still running (or after
it times out), then retry `terraform destroy -auto-approve`:

```bash
# List all security groups still in the VPC
aws ec2 describe-security-groups --region us-east-1 \
  --filters "Name=vpc-id,Values=<vpc-id>" \
  --query 'SecurityGroups[*].{Name:GroupName,ID:GroupId}' \
  --output table

# Delete each k8s-* security group (do NOT delete the 'default' SG)
aws ec2 delete-security-group --region us-east-1 --group-id <sg-id-1>
aws ec2 delete-security-group --region us-east-1 --group-id <sg-id-2>

# Retry the destroy — it will pick up where it left off
terraform destroy -auto-approve
```

**Note:** The VPC ID can be found in Terraform state or outputs:
```bash
terraform output vpc_id
```

### `seccompProfile` violates PodSecurity restricted policy

**Symptom:**
```
pods is forbidden: violates PodSecurity "restricted:latest":
seccompProfile (pod or containers "migrate", "chat-api" must set
securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
```

**Cause:** The `chatapp` namespace enforces the `restricted` Pod Security
Standard. The pod and container `securityContext` blocks were missing
`seccompProfile.type: RuntimeDefault`.

**Fix:** Added to `chatappinfra/templates/helm-values.tftpl` under both
`api.securityContext` and `api.containerSecurityContext`. Already present
in generated `values-prod-infra.yaml`.
